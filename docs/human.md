# 真人滑块验证（全站门禁）

← 返回 [README](../README.md)

一句话：**所有页面与接口都要先拖一次滑块**，通过后本机签发一枚匿名的签名 cookie，
12 小时（后台可改）内不再问；搜索引擎爬虫按"UA + 反查 DNS"豁免，所以 SEO 还在。
后台 `/admin` 是**先过滑块、再要口令**两道。

## 它挡得住什么、挡不住什么

这是这个功能唯一需要认真对待的问题，否则上了验证码反而更放心。

| | 说明 |
| --- | --- |
| 挡得住 | 直接 `GET` 页面/接口的脚本、无差别抓站的爬虫、把这里当免费影视搜索 API 刷的人。它们要么没有 cookie，要么得先实现"取挑战 → 按服务端给的缺口位置拖进容差 → 带耗时与轨迹采样提交"这一整套，而且挑战**两分钟过期、提交一次就作废**，失败多了按来源冷却（10 分钟内 10 次）。 |
| 挡不住 | 铁了心的人。挑战与校验都在这台机器上，照着 [slider.js](../zhuiju/static/slider.js) 发请求就能过；服务端能确认的只有"这枚 cookie 是不是我签的、有没有过期"。 |

所以它换来的不是"安全"，是两样更实际的东西：

1. **把无成本滥用变成有成本滥用** —— 配上门禁前就有的按 IP 限流，够劝退绝大多数；
2. **后台第一次有了"这是真人"的硬凭据** —— 以前分真人和脚本全靠猜 UA（见
   [docs/admin.md](admin.md) 的「真人、脚本，还是说不清」），现在 `queries.verified=1`
   那些行是当场拖过滑块的，可以拿它反过来校准猜的那套准不准。

## 三处口径

- 挑战与 cookie 的签发/校验、爬虫豁免名单：[zhuiju/human.py](../zhuiju/human.py)
- 门禁挂在哪里、豁免哪些路径、放行方式怎么记：`zhuiju/app.py` 的 `_human_gate`
- 开关与有效期：后台「设置」（存在 `zhuiju/data/settings.json`，`ZHUIJU_HUMAN_GATE` /
  `ZHUIJU_HUMAN_HOURS` 环境变量优先）

## 门禁的边界（这几条是刻意留的口子）

- **放行前缀**：`/static/`（验证页自己要加载样式和脚本）、`/api/human/`（门禁不能挡自己，
  否则出不去）、`/robots.txt`（挡了等于自断收录）、`/admin/logout`（被锁在外面的人也要能登出）、
  `/strm/` 与 `/api/strm/`（Emby STRM 的搬运口）。
  后面这两条是必须的：拿它们的是 NAS 上的同步脚本，`curl` 拖不过滑块；而这两组路径里没有页面，
  挡住的结果是 `/strm/zip` 回一段**状态码 200 的 HTML** —— 脚本会存下一个几 KB 的"假 zip"，
  比直接 403 难查得多。这些包里只有各家采集站本来就对外公开的 m3u8 地址，包名又是
  `movie01`、`tv01` 这种连续编号，放行并不改变暴露面。
- **接口回 423**，不回 401/403：这不是"没权限"，是"还不知道你是不是人"。前端 `getJSON`
  里只有一处出口，收到 423 就弹滑块，通过后自动重跑刚才那次搜索（不用重新输关键词）。
- **被 423 挡掉的请求不进统计**：没真的搜过任何东西，记一条就是假数。
- **验证页自己带完整的 SEO 信息**（title / description / canonical / `index,follow` /
  WebSite + SearchAction 结构化数据）。正常情况下真爬虫走豁免到不了这一页；万一哪天
  "UA + 反查 DNS"那条判据不准了，这一页是它看到的站点门面，而不是一个把收录掐死的死胡同。
- **内网与回环不豁免爬虫**：真搜索引擎不会从科室局域网里出来，这条顺手挡住了
  "本机跑个脚本挂个爬虫 UA 就绕过门禁"。

## cookie 里有什么

只有一个带到期时间的 HMAC 签名（`<到期 unix 秒>.<签名>`），用配置文件里的会话密钥签，
**不含姓名、账号、搜索内容，不落盘、不进统计库**。统计库只多记一列 `verified`：

| `verified` | 含义 |
| --- | --- |
| `1` | 带着有效 cookie 的人（当场拖过滑块） |
| `0` | 搜索引擎爬虫豁免（确实是机器，按 SEO 规则放过去） |
| `NULL` | 门禁关着，或者这批记录是门禁上线之前攒的 |

三种必须分开：把"门禁没开"写成 `0`，就等于说"关掉开关的这段时间全站都是机器人"。
后台总览那一格把这三条各数一个数，加起来就是当前条件下的总条数，能当场复核。

## cookie 绑设备

签名里除了到期时间还有一段**设备指纹** = `来源地址 + 系统 + 设备类型`（`human.fingerprint()`）。
每次请求都按**当前这次请求**重算一遍再比，所以对不上就是没验过：

- 把那枚 cookie 拷到另一台电脑 → 来源地址变了（通常系统/设备类型也变）→ 用不了；
- 同一台电脑、浏览器自动升级（Chrome 124 → 131）→ **照样能用**：指纹里刻意不含版本号，
  不然每次浏览器升级就把全科室踢下线重拖一次；
- 同一台电脑换个浏览器（系统/设备类型算出来不同）→ 要重验；
- 笔记本换网络（IP 变了）→ 要重验一次，之后 12 小时不再问。

诚实的边界：这是**纯 cookie 方案能做到的上限**。在同一台机器、同一个网络里把整枚 cookie
连值带上下文一起复刻（比如同一个 IP 上换个进程冒充同样的 UA 家族）是拦不住的 ——
要真做到"物理设备绑定"得引入客户端证书或硬件信号，那是另一个量级的决定。

## 无障碍

滑块只给鼠标用户用是不合格的。点一下滑块后用**左右方向键**也能拖过去（停手 0.6 秒自动提交），
服务端对应的是"按键次数够 6 次"这条替代证据 —— 比指针轨迹弱，但这是给人留的门，
不是给脚本留的门（脚本本来就能伪造轨迹，见上面那张表）。

## 关掉它

后台「设置」里把「真人滑块验证」选成"关"。关掉之后全站对脚本敞开，页面上那行说明也写明了这点，
只建议在纯本机自用（`127.0.0.1`）时关。改完立刻生效、不用重启。

## 上线后立刻被用户抓出来的两个坑（都记在这儿，别退回去了）

1. **"一直说我太快了"** —— [slider.js](../zhuiju/static/slider.js) 的 `pointerup` 里先把计时起点
   清零，再调 `submit()`，而 `submit` 里现算"现在减起点"，于是每次都上报 `ms=0`，
   服务端按"太快了"永远拒。键盘那条路反而能过（它没提前清起点），所以现象是"鼠标拖不过、方向键能过"。
   现在改成**先把用时记进 `spent` 再清起点**，提交只读 `spent`。
   同时把 `MIN_MS` 从 320 降到 200：手快的人"啪"一下拖过去是真实存在的，门槛抬太高就变成谁都用不了，
   主判据本来就该是采样点数（一次真拖拽有几十次 move）。
2. **"缺口和滑块不匹配"** —— 缺口的位置和宽度原来是拿一个写死的 44px 在 CSS 里算比例的，
   而窄屏 CSS 把滑块加宽到 52px（拇指目标），两边就对不齐了；再加上缺口是按"左边缘"定位的，
   中心比目标位置偏了半格。现在宽度**现量** `knob.offsetWidth`，缺口按像素画并且**以目标为中心**，
   窗口大小变了还重算一遍；`--kw` 只在轨道那一处定义，滑块和缺口都从它取。
