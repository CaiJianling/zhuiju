## Emby STRM：把近一年的资源导成 Emby 媒体库

需求口径是「每天后台采集近一年的电影/电视剧，m3u8 拼成 Emby 认得的 strm，电影一套、
电视剧一套，多个能播的源都挂上、播放前能选线路，数据先进库再导出，后台能设时间范围，
太大就分卷并在接口里体现（movie01、movie02…）」。落地方式：**采集 → SQLite → 导出 → 打包**
四步，每步都能单独跑。

### 为什么是"翻更新流"而不是"按分类翻"（三条实测）

- `ac=list&t=分类ID` 这条路在各站都不成样子：火狐 `t=2` 只给 1 条、`t=1` 直接 0 条，
  别的站要么空要么和总列表一样。而全局更新流 `ac=videolist&pg=N` 严格按 `vod_time`
  倒序、实测能稳定翻到 4800 页 —— 所以枚举只能"从最新往回翻，翻到窗口外为止"。
- `ac=videolist` **一次请求就把元数据和全部播放线路带回**（`vod_play_url` 只在 videolist 里有，
  `ac=list` 里没有），所以采一遍只要 N 次请求，不需要先取 ID 再逐条 `ac=detail`。
- 17 个源全部支持这个形状；`limit` 被硬限在 20（给 50 会裁回 20，给 100 直接超时）。
  顺带一提：索尼、闪电那两个"关键词搜索被站点关了"的源（见 `zhuiju/sources.py` 的
  `searchable`），更新流是好的 —— 本功能只翻更新流，所以它们照样收得到。

### 目录与命名（这是能不能刮削出来的关键）

```
strm/movie/movie01/毒液：最后一舞 (2025)/毒液：最后一舞 (2025) - 虎牙资源.strm
                                                       └─ 同一文件夹里另一个源 = Emby 的"多版本"
strm/tv/tv01/庆余年 第二季 (2024)/Season 02/庆余年 第二季 (2024) - S02E03 - 虎牙资源.strm
strm_zips/movie01.zip  →  毒液：最后一舞 (2025)/毒液：最后一舞 (2025) - 虎牙资源.strm
strm_zips/tv01.zip     →  庆余年 第二季 (2024)/Season 02/…          # 默认不带卷号目录
```
盘上的树是 `strm/<类>/<卷>/片名 (年份)/…`；**包里的路径默认只到 `片名 (年份)/…` 这一层**
（既不带 `movie/`、`tv/` 那层分类目录，也不带 `movie01/` 卷号目录），因为包是"解压到媒体库根"
用的，而 Emby 的常规布局就是媒体根下面一个文件夹一部片。后台「包内带卷号目录」打开后会多一层
`movie01/`，好处是"这一卷不要了"能整目录删掉；改这一项会重打所有卷，已经解压过的别改——
旧路径那套还留在库里，同一部片会以两个路径各出现一次。

Emby 认多版本的条件是：同一条影片的几个文件放在同一个文件夹里，文件名**以文件夹名开头**、
后面接 ` - ` 再接版本说明（剧集是 `<剧名> - S01E01 - 版本名`），` - ` 后面那段就是客户端
里选线路时显示的字样。写成别的形状（比如把线路名塞在年份前面）会被认成两部影片，
海报墙上出现两张一模一样的海报，比不合并还糟。**一个 strm 只能对应一部片/一集**
（Emby 扫文件名入库，文件内容只有一行地址），所以"近一年全量"必然是几十万个小文件，
不可能塞进一个大 strm —— 分卷就是为这件事准备的。

不写 NFO：strm 那条路上 Emby 认的是"文件夹名/文件名"，目录里再放一份 NFO 对它没有额外价值
（实测包里每部片一份 NFO 只多约 0.4KB，但要多写 4312 个文件、多一倍条目，还要为海报去扩
图片代理的白名单）。想让 Emby **不用猜**、直接锁定某一部片，靠的是下面那一节的名字里带 ID。

### 一部片算电影还是剧集（各源说法不一致时）

`kind_of_rows()` 管这件事。为什么要有它：以前取的是 `ORDER BY src_name` 第一行的 kind，
等于**用中文源名的字节序决定一部片进电影库还是电视剧库**。实测库里 11 个 key 各源类别不一致
（《疯狂动物城2》电影天堂标电影、两家非凡标动漫；《鬼的新娘》三家给"正片"、淘片给 10 集；
《我的美食向导 第二季》备番给 4 集）。判据从硬到软，找到第一个能定案的证据就停：

1. **有任何一家给了超过 `MOVIE_EP_MAX`（3）集** → 剧集。按电影布局只会留一集，整部剧就丢了；
   而且真剧集会随更新越攒越多，这一条自动生效。
2. **所有集名都"像版本、不像集"**（`HD中字 / HD国语 / HD粤语`、`TC中字`、`正片`）→ 电影。
   这条是决定性的：《疯狂动物城2》三个源给的那"三集"其实就是同一部片的三个版本，
   两家的"动漫"分类不能把它变成剧集。
3. **片名里有「剧场版 / 电影版 / 特别篇」→ 电影；有「第 X 季 / Season」→ 剧集**。
   库里《完美世界剧场版九劫焚天》就是靠这条从剧集搬回电影的。
4. 都没有证据就按各家 `type_name` 投票，**平票算剧集** —— 站点的"电影"分类常拿来塞
   网络大电影和短片，而"动漫 / 剧 / 番"这类标签基本只在真是剧集时才出现；
   往剧集倒也不丢内容（每集还在，只是布局变了）。

判出来换了类别时，导出会把另一类别那一条 `part` 卷号放掉（不然它一直占着那一卷的名额，
而且哪天又投回电影，会被塞回几周前那一卷）。这一步会搬家：旧路径删、新路径写，
实测影响库里 3 个 key、14 个文件。验证在 `tests/test_strm.py` 第 17 节（10 项，
全部照库里真实形状造的数据：HD中字/HD国语/HD粤语 那一组就是这么抄下来的）。

### 名字里带 ID（`[tmdbid=…]` / `[doubanid=…]`）

Emby 能从文件夹名/文件名里直接读一个元数据站的 ID，读到就跳过"按片名+年份去搜"这一步
—— [Movie Naming](https://emby.media/support/articles/Movie-Naming.html) 和
[TV Naming](https://emby.media/support/articles/TV-Naming.html) 列了 `tmdbid` / `imdbid` /
`tvdbid` 三种标签，`[tmdbid=157336]` 与 `[tmdbid-157336]` 两种分隔都认。
同名翻拍片、只有年份的片子最容易认错，这一条就是治它的。

**上游给不了这个号。** 实测各家 `ac=videolist` 一条有 83 个字段，和外部 ID 有关的只有
`vod_douban_id` 一列，没有 tmdb/tvdb/imdb；而且豆瓣号很稀：库里 11706 行只有 548 行带（4.7%），
按去重后的片算是 4312 部里 440 部（10.2%）。更要紧的是 **Emby 本体不认 `doubanid` 这个标签**
（要装豆瓣刮削插件、或换 MoviePilot 那类工具才吃）。所以两颗开关各管一件事：

| 开关 | 写出来 | 要不要联网 | 谁认 |
|---|---|---|---|
| `tag_douban_id` | ` [doubanid=38185414]` | 不用，上游就有 | 豆瓣插件 / MoviePilot |
| `tag_tmdb_id` | ` [tmdbid=157336]` | 要查 TMDB | **Emby 本体就认** |

布局按前面那两条规则来，**不能只带一边**：

```
电影   星际穿越 (2014) [tmdbid=157336]/星际穿越 (2014) [tmdbid=157336] - 虎牙资源.strm
       └─ 目录名和文件名都带。只带在文件上，"文件名以文件夹名开头"这条多版本判据就破了
剧集   绝命毒师 (2008) [tmdbid=1396]/Season 01/绝命毒师 (2008) - S01E01 - 虎牙资源.strm
       └─ 只带在剧集根目录那一段。Emby 读剧集就认这一个，每集文件名再带一遍
          等于把 60 集 × N 源的路径全拉长，容易顶到 Windows 的 260 字符上限
```

两个都开且两个号都有时**只写 tmdbid**：标签的作用就是"绕过名称搜索"，一个够了，
挂两个只会把名字推长（豆瓣插件那批人本来就会按自己的方式配）。
上游没给号、TMDB 也没查到的片子照旧只写 `片名 (年份)`，**不会塞一个猜来的号**。

**查 TMDB 这一支**（`tools/collect_strm.py` 的 `resolve_ids()`）：一部一次请求、跟着采集
一起 sleep、一轮最多查 `tmdb_per_round` 部（默认 120），预算固定留两成给它——不留就被翻页
吃满了；采集提前收完时剩下的时间全给它。手动单跑：`python tools/collect_strm.py --ids-only --budget 600`。

- 域名默认 `https://api.tmdb.org/3`：实测 `api.themoviedb.org` 在这台机器上 TCP 直接超时，
  而 `api.tmdb.org` 通（回 401，只差 key）。你那边出不去就改后台「TMDB 接口地址」。
- key 存在 `strm.db` 的 setting 表里，**页面上不回显**（留空=不改，判据在 `save_settings`），
  也支持环境变量 `ZHUIJU_TMDB_KEY`。两颗开关都开着但 key 没配时采集那一支直接跳过，
  不会白留两成预算空转 —— 这正是"设置了却没生效"里最难发现的一种。
- **命中判据只有两条**：片名归一化后完全相等（拿的是跨源合并那把钥匙 `search.title_key`，
  TMDB 的 `title` 与 `original_title` 都比一遍，因为 `language=zh-CN` 时谁中文谁英文不固定），
  并且落档年份对得上。名字对不上却塞一个号进目录名，Emby 会照着这个号命中，
  等于把一部片指到另一部片上 —— 那比没号严重得多（没号它自己还会去搜）。
- 结论写在 `idmap` 表里，一个片名一行：`ok`（命中）/ `none`（查过确实没有）/
  `bad`（没打成：key 不对、超时、限流）。`none` 不再重查，`bad` 到 `tries=3` 封顶；
  连着三次打不通就整支提前收。TMDB 后来收了这条片，就按后台那颗
  **「重查 TMDB 说「没有」的那些」**（`POST /admin/strm/recheck`：清掉 `none` 并顺手起一轮）。
- **查到一个新号必须把这个 key 标脏**（`save_id` 返回的就是这件事）。不标脏它就不在增量
  导出的待办名单里，号永远进不了目录名 —— 表现是"查到了三轮名字还是没变"。
  实测踩过：`save_id` 只写 idmap 不标脏，导出的 `keys` 里根本没有这一部。

改这两颗开关都要跑一次**全量重建**（后台那颗按钮）：带标签=换路径，旧路径的文件会被删掉、
新路径重写，Emby 那边等于这些片重扫一遍（观看进度、收藏会跟着丢，切之前想清楚）。
已经查到的号存在库里，不会因为这个丢。

### NFO：每个 strm 旁边一份同名的 `.nfo`

开关是 `write_nfo`（默认开）。要的就是**同名**这一件事 —— Emby 认的是"media 文件的
sidecar"，`x.strm` 配 `x.nfo`，名字差一个字它就不读，所以同一个文件夹里几个源就有几份
内容几乎一样的 NFO（每一份都对应该文件）。三种根标签按 Emby/Kodi 的写法来，不自己发明：

```
movie/movie01/星际穿越 (2014) [tmdbid=157336]/
    星际穿越 (2014) [tmdbid=157336] - 虎牙资源.strm
    星际穿越 (2014) [tmdbid=157336] - 虎牙资源.nfo     <movie>  这一部片的完整元数据
tv/tv01/绝命毒师 (2008) [tmdbid=1396]/
    tvshow.nfo                                          <tvshow> 系列级的号只能写在这儿
    Season 01/绝命毒师 (2008) - S01E01 - 虎牙资源.nfo    <episodedetails> 只有季号与集号
```

剧集为什么要两份：**系列的 ID 不能写进某一集的 NFO** —— 那一集里的 `uniqueid` 表示
"这一集的号"，塞系列号等于给每一集发一个错的身份证。所以 `tvshow.nfo` 承载
`tmdbid` / `doubanid` / 简介 / 演员，`<episodedetails>` 只写 `showtitle` + `season` +
`episode` + 集名，顺带避免 13 万个文件各抄一遍同样的大段文本。

每份 `<movie>` / `<tvshow>` 里的字段全部来自上游 `ac=videolist` 那一次请求（不额外联网）：
`title` / `originaltitle` / `sorttitle` / `year`、`premiered`+`releasedate`（只有
`vod_pubdate` 精确到日才写 —— 只有年份时硬凑一个 1 月 1 日就是假数据）、`genre` /
`country` / `director` / `actor` / `plot` / `rating`（上游填 "0.0" 的相当多，0 不当分）/
`thumb` / `studio`（这条片来自哪几家源，地址失效时在界面上能认出来）。

两个坑是实测过的，别写回去：

- **海报写上游原地址，不走本站 `/img`。** 抽样 12 张真图不带 Referer 全回 200
  （`pic.youkupic.com` / `image.huyajs.com` / `fffgood.com`），这些采集站的图床不像豆瓣那样认
  Referer；而走代理就得把每部片的地址登记进白名单，那份清单是**每个进程各自一份**的，
  片数一多会把首页那些图挤掉，还会出"web 进程下一次渲染又把清单裁回上限"这种事。
- **元数据变了要能重写 NFO，但不能因此让采集以为翻到了新片。** 所以有两个指纹：
  `sig`（播放地址）决定采集的增量早停，`msig`（元数据）只决定"这一部要不要重新导出"。
  合成一个的话，上游哪天补了简介就会让那几千页被当成"全是新内容"重标脏。

老数据补一次就够：那些行所在的页码游标早就翻过去了，增量早停让它们不会被重新采到，
不专门补就永远只有片名和年份。走 `ac=videolist&ids=a,b,c`（实测一次能带 20 条完整条目）
按源批量问，**一轮手动 `python tools/collect_strm.py --backfill-only --budget 240` 约能补
两千多条**；上游已经不认的 ID 会把 `msig` 写成 `gone` 哨兵，免得每轮当"还没补"重问。
开了 NFO 时，每轮结尾会把还差多少条报出来（没开 NFO 就一句不提，那是纯噪音）。

代价要说清楚：开这一项之后**文件数与包里的条目都翻倍**（实测见下面「实测规模」），
Emby 扫库也要多读一倍的东西。只要目录名里已经带 `[tmdbid=…]`、且让 Emby 自己联网刮削，
关掉它更省。关掉时已有的 `.nfo` 会被删干净，设置和盘上不会各说一套。

### 采集节奏：慢速 + 断点续采（一轮跑不完是设计内的）

`tools/collect_strm.py` 每轮有预算（默认 900 秒），每次请求之间 sleep（默认 400ms），
并发只开 3 个源，而且是**轮转换手**：每个源一次只翻 8 页就换下一批上。

为什么不是一次把所有源交给线程池：实测 10 分钟只有 4 个源有数据 —— 3 个 worker
各抱住一个源翻到预算结束，剩下 13 个源整轮都在排队。改成轮转之后，120 秒的一轮
就能把 17 个源各推 8 页。近一年的量本来就要跨天续采，**公平比深度重要**：
先让每个源都往前挪，"多个源都能选线路"这件事才提前成立。

每个源翻到第几页记在 `strm.db` 的 `cur` 表里，预算用完就停，下次访问接着这一页翻。
某个源只要完整翻出过一次窗口（`backfill=1`），之后的轮次
连续几页"全是老片且一条地址都没变"就提前收，不必天天把一整年重翻一遍。

**只有真翻到窗口外才清库**（`prune_source` 删掉这一轮没再见到的条目 = 上游下架或掉出窗口）。
提前收那一支刻意不清：那时只翻了开头几页，后面那些是几天前采的正常数据。

到量就合并：每 150 次请求或每 240 秒导出一次，一轮结束再导出一次。导出只处理 `dirty=1`
的那些片，内容签名没变的文件不重写（Emby 那边 mtime 不动，就不会把整个库重扫一遍），
打包同理 —— 卷的内容哈希没变就不重打。实测把全库 5,938 条重新标脏再导一次，
72,994 个文件全部判成"未变"，11 秒走完。

**导出与后台写同一个库，事务必须切碎。** SQLite 开了 WAL 也只允许一个写者，
而导出是"写几万个文件 + 更新 file 表"的长活。一开始把所有写入攒到最后一次提交，
结果后台点"保存设置"直接 500（`database is locked`）；把锁反过来压也不该让采集白跑。
现在的做法：导出每 200 部提交一次、打包每卷提交一次、写文档前再提交一次；
`save_settings` 遇到锁重试 6 次（约 8 秒）后仍不行就回一句人话
（"没写进去：采集/导出正在占用数据库，稍等一下再保存"）而不是抛异常；
导出这一侧抢锁失败也只重试并留着 `dirty` 标记，等下一次合并 —— 已经采到的数据不会因为这一次
没导成就丢掉。验证：`tests/test_strm.py` 第 11b 节用另一条连接按住写锁跑这三个断言。

### 接口

| 地址 | 给什么 |
|---|---|
| `GET /api/strm/download` | **扁平下载清单**：`{"Movies": {"movie01.zip": "url", …}, "TVs": {"tv01.zip": "url", …}}`，脚本直接遍历下载用 |
| `GET /api/strm/manifest` | 两类各有哪些卷、每卷多少部/多少文件/包多大、下载地址、当前设置与游标 |
| `GET /api/strm/index?kind=movie&part=movie01&page=1&per=200` | 这一卷里有哪些片、各有几条线路、文件在哪 |
| `GET /api/strm/tree?kind=tv&part=tv01` | 这一卷所有 strm 的相对路径，一行一个（`curl` 给脚本用） |
| `GET /strm/zip?name=movie01.zip` | 下载分卷包（`Content-Disposition` 里就是裸卷名 `movie01.zip`） |
| `GET /strm/file?path=movie/movie01/…/x.strm` | 只取单个 strm 文件 |
| `GET /api/strm/status` | 在不在跑、上次跑了多少页、库里多少条、待合并多少 |

`/api/strm/download` 里的地址**跟着你这次是怎么访问的走**：用 `http://123.com` 打开，
URL 就是 `http://123.com/strm/zip?name=movie01.zip`；带端口照抄端口；走本机 nginx 反代时
按 `X-Forwarded-Proto` / `X-Forwarded-Host` 出 https 与对外域名（只采信上一跳是回环地址的
转发头，否则任何人都能伪造这个头）。想只要相对地址，加 `?abs=0`。
清单里只列**盘上确实有文件**的那些卷 —— 下载清单不该塞死链；某卷没文件的真实状态去
`manifest` 与 `/strm/zip` 的 404 里看。

```bash
# 拷到 NAS 上批量下载
curl -s http://123.com/api/strm/download | jq -r '.Movies[], .TVs[]' | xargs -n1 curl -O
```

**这几条路径是全站真人门禁的豁免前缀**（`app.py` 的 `HUMAN_EXEMPT` 里有 `/strm/` 与
`/api/strm/`）。必须豁免：拿它们的是 NAS 上的同步脚本，`curl` 拖不过滑块；而这两组路径里
没有页面，被挡时 `/strm/zip` 回的是**状态码 200 的滑块 HTML** —— 脚本会存下一个几 KB 的
"假 zip"，比直接 403 难查得多。包里的地址本来就是各家采集站对外放出来的 m3u8 直链，
包名又是 `movie01`、`tv01` 这种连续编号，放行并不改变暴露面。规则细节见
[docs/human.md](human.md) 的「门禁的边界」。

`/strm/zip` 不拿请求里的名字直接拼磁盘：先按 `movieNN.zip` / `tvNN.zip` 这个形状认
（NN 就是卷号，两位补零：movie01、movie02…、tv01、tv02…），
再去 `zip` 表里查这一卷确确实实打出来过 —— 否则就成了任意文件下载。

### 后台那一节（/admin → Emby STRM）

采集开关、**采集时间范围（天）**、只要 m3u8、每源几条线路、每部最多几集、每卷最多几个文件、
NFO 开关（每个 strm 一份同名 .nfo）、两颗 ID 标签开关与 TMDB 的 key/地址/每轮部数、
每轮预算、请求间隔、并发数、最小间隔、
排除哪几个源，都存在 `strm.db` 的 `setting` 表里，保存即生效。
同一节里还能立刻催一轮采集、手动导出、全量重建。
这些设置放库里而不是 `data/settings.json`：`strm.db` 本身就是"删了重采就行"的机器状态，
两边放在一起，改窗口和看游标在同一页上完成。

开关的语义要说清楚：**关掉是"不再起新的一轮"，不是"打断正在跑的那一轮"** ——
正在翻的那个进程会把它自己那一轮的预算跑完（最长 `budget_seconds`）。
要真停就得结束那个进程（`logs/strm.lock` 里记着它的 PID）。

进度是**就地更新**的：这一节在页面加载后自己每 10 秒问一次 `/api/strm/status`
（闲下来降到 60 秒，标签页切走就不问），状态行、库计数、ID 与 NFO 那两句话、各源游标那张表
都只换文字和行，不整页重载；一轮结束的那一刻再拉一次 `/api/strm/manifest` 把分卷表刷新。
禁用 JavaScript 时这一节仍然说得清在不在跑 —— 那四种说法本来就是服务端渲染的。

**这一节里的表单与按钮也全部是异步提交的**（`bindForms()` 拦住 submit 走 fetch）。
之前它是普通表单提交 + 服务端 302，而那条 redirect 只带了 `#strm` 锚点、没带
`tab="strm"` —— 整节的显隐是 CSS 按 `body[data-tab]` 决定的，锚点救不了一个被 `display:none`
藏起来的块，于是"点保存 → 页面回到总览"，看着就像没保存上。现在：带 JS 时页面根本不动，
提示和那几个数就地换；没 JS（或接口没答话）时退回表单提交，而那条 redirect 带着
`tab="strm"` 会正确回到这一节。JSON 回包里除了提示还带着 `lines`（ID / NFO 那两句话），
这两句由 `strm.status_lines()` 在 Python 里拼 —— 模板拼一份、JS 再拼一份迟早会对不上，
最坏的一种是页面说"没配 key"而 JS 说"已配"。

顺带一条会咬人的行为：**表单提交的是页面上当时那份值**。开着旧页面去改库（或者旧页面
本来就没有某一颗开关），回来点一次保存就会把那几个键按旧值写回去。改完设置后那句提示
会列出当前生效的几个关键值，就是给人核对用的。

### 实测规模（决定你该怎么设那几个数）

- 100 秒 × 3 个源的一轮：111 页、入库 1204 条（668 部）、导出 17510 个 strm、打 7 个卷。
- 120 秒 × 17 个源（轮转，每源 8 页）的一轮：105 页、入库 1540 条、库里累计 4751 条 / 2201 部，
  导出写 30887 个文件、重打 7 卷。也就是**每 100 秒量级就是万级文件** ——
  文件数 = 集数 × 源数，长剧集是主要放大项。
- 导出这一步不便宜：几千个文件要落盘，实测每部片约 0.5 秒（写文件 + 建目录 + 算签名）。
  所以一轮的墙上时间里大头常在导出，而不是发请求；这也是"内容没变就不重写"要较真的原因。
- 一年窗口 ×17 个源要翻两三万页，按默认节奏是几个小时到一两天的累计采集量。
  首轮不必等齐：轮转换手意味着跑两三分钟就能看到全部 17 个源的近两周条目。
- `part_files` 默认 20000。**包的大小由文件名说了算**：实测 tv01 那一卷 28,700 个条目，
  正文（一行 m3u8 地址）才 1.8MB，zip 却有 9.5MB —— 中文长路径每条要写两遍
  （本地头 + 中央目录），一个条目光名字就 250 字节上下。所以别指望"文件多包就小"，
  真正该在意的是卷的数量（今天 7 卷，够用）和解压时的文件数（Emby 扫库要一个个认）。
- 想小一点就先动这三个：时间范围（365→180）、每部最多几集（120→40）、排除几个源。
- **NFO 到底多重**（一次全量重建实测：库里 11,706 条 / 4,312 部）：
  单集那份 `<episodedetails>` 平均 **221 字节**（只写季号集号与集名），
  电影那份 `<movie>` 平均 **1,078 字节**，`tvshow.nfo` 平均 **1,029 字节**。
  整棵树从 **136,307 个文件变成 276,325 个**（strm 136,307 + NFO 140,018），
  落盘 40.4MB（strm 本体的正文才 8.2MB —— NFO 是正文的 1.9 倍重量）；
  七个包从 54MB 变成 **106.7MB**，条目翻倍：`tv01.zip` 17.2MB / 48,613 条 →
  37.96MB / 98,563 条，`movie01.zip` 0.39MB → 1.45MB。
  那次全量重建（写 118,806 / 未变 157,519 / 删 50,046）跑了 **1,355 秒**。
  也就是说代价主要落在**文件数（inode、同步脚本要拷的条目、Emby 要扫的个数）**上，
  包体积大约翻倍但不至于失控。不需要本地元数据就关掉 `write_nfo`，
  已有的 `.nfo` 会在下一次导出时全部删掉，包会退回 54MB 那一档。
- **NFO 的字段有多半取决于元数据补没补**：库里 11,706 条里还有 9,054 条没补过简介/演员
  （那是补字段之前采进来的旧行），它们的 NFO 就只有片名、年份和 ID。
  部署到新机器上时这几条按顺序跑：`--backfill-only --budget 600`（补旧条目的元数据，
  一次问 20 条）→ 后台填好 TMDB key 后 `--ids-only --budget 600`（补 tmdbid）→
  最后 `--export-only --full` 一次性写出来。不开 NFO 时前两步都可以省。
- **打开 ID 标签那一轮的开销**（实测，库里 11706 条 / 4312 部、136307 个文件）：
  全量重建跑了 1703 秒，其中"写 42485 / 未变 93822 / 删 46797"—— 只有那 440 部带豆瓣号的
  换了路径（其余的签名没变，一个字节都不重写），删掉的 46797 里含改名前的旧路径和
  之前在盘上的 4312 份 NFO。包体积基本没动（tv01 从 17.0MB 到 17.2MB），
  因为多出来的只是每条路径里那 18 个字符。

### Emby 侧怎么接

1. 把 `movie01.zip`、`movie02.zip`… 全部解压到同一个「电影」库根目录，
   `tv01.zip`、`tv02.zip`… 解压到同一个「电视剧」库根目录（新增的卷解进同一目录再扫一次库，
   不用新建库）。解出来就是 `电影库根/片名 (年份)/片名 (年份) - 虎牙资源.strm`，
   正好是 Emby「一个文件夹一部片」的常规布局。或者直接把这个项目里的 `strm/movie`、`strm/tv`
   挂给 Emby —— 那一棵树多一层卷号目录，Emby 会往下找，不影响识别。
2. 以后每天：上游换地址/出新集，靠下一轮采集重写文件，然后让 Emby 做一次
   「扫描新建和更新的文件」即可。
3. strm 里写的就是上游的 m3u8 直链，**播放不经过本站**，所以本站停了也只影响"更新"，
   不影响已经在库里的条目能不能播。

验收这套东西：`.venv\Scripts\python.exe tests/test_strm.py`（全离线，244 项检查，
含"游标 SQL 占位符数量"和"TMDB 命中判据能不能把片认错"这种一跑就出事的坑）；
看现状：`.venv\Scripts\python.exe tools\collect_strm.py --check`（会把 ID 这一项查到什么
程度、还剩多少没查一起打出来）。
